FAQs

Plain-English answers for product, operations, and business stakeholders evaluating the synthetic tank telemetry API, CLI, MCP, webhook, and governance concept.

What is this, in plain English?

This is a synthetic demo showing how tank telemetry data could become safely programmable. The existing portal stays in place for human users, while API, CLI, MCP, and webhook surfaces make the same operational data usable by software systems, support teams, integration teams, and approved agents.

Are you trying to replace the existing portal?

No. The thesis is the opposite: keep the portal. The portal remains the human interface. This demo shows a governed programmable layer beside it so integrations, support workflows, and agent-assisted workflows do not depend on manual portal clicks.

Is this using vendor, customer, or proprietary data?

No. Everything is synthetic. There is no customer data, no real addresses, no real device IDs, no screenshots, no logos, no scraped portal content, and no proprietary records. It is a product-direction demo, not a clone or reverse-engineered system.

Why would this matter to a telemetry business?

It creates a customer-facing integration path for operational telemetry. Instead of relying on CSV exports, manual portal checks, or one-off integration work, customers could connect tank inventory, alarms, diagnostics, runout risk, and delivery signals directly into their own dispatch, ERP, analytics, and operations systems.

Who would use each surface?

The portal is for customers and operators. The API is for software and integrations. The CLI is for support, QA, product, and engineering teams. The MCP layer is for approved AI agents. Webhooks are for event-driven integrations.

Could this help customers directly?

Yes. That is the core customer value. In a production version, customers could ingest near real-time telemetry into their own systems without waiting for CSV exports or manually copying portal data. The portal remains the human surface, while APIs, webhooks, and governed assistant workflows let customers connect inventory, alarm state, runout risk, and delivery signals into dispatch workflows with drivers, internal operations tools, ERPs, and reporting systems.

What is MCP, and why should a manager care?

MCP is a way to expose approved tools to an AI assistant. Instead of giving an agent broad browser access, the platform can expose narrow read-only tools such as get tank status, summarize alerts, or explain delivery priority. That makes agent use controlled, inspectable, and future-ready instead of improvised.

Can the agent operate the same workflows as the CLI?

Yes. The CLI proves repeatable operator and support workflows, and MCP exposes those same workflows as approved agent tools rather than raw terminal commands or browser automation. For example, tankctl tanks at-risk --days 7 maps to an agent-callable tool such as list_runout_risks(days=7). That future-proofs the platform because new agents can call stable, named tools instead of scraping the portal or inventing their own process.

Could an agent accidentally change something important?

Not in this demo. It is read-only. In a production system, the safe pattern is to separate recommend or propose from approve and execute. Future write actions, such as changing thresholds, acknowledging alarms, moving tanks, notifying customers, or creating delivery orders, should require explicit scopes, tenant boundaries, audit logs, and human approval.

What is the business outcome?

Customers can move near real-time tank telemetry into the systems where work actually happens, without waiting for CSV exports or manually copying portal data. That means inventory, alarm state, runout risk, diagnostics, and delivery signals can feed dispatch planning, delivery driver workflows, ERPs, reporting, support diagnostics, and approved integration partner workflows. The portal stays intact, but telemetry becomes operationally useful outside the portal.

How is this different from just having an API?

An API is only one interface. The larger idea is a governed programmable layer: API for systems, CLI for repeatable internal workflows, MCP for approved agents, webhooks for event-driven integrations, and policy boundaries for safety. Future agentic workflows need clear tool semantics, permissions, event triggers, auditability, and human-in-the-loop controls, not just endpoints.

Is this production-ready?

No. It is intentionally a concept demo. A production version would need identity, tenant scoping, authorization, audit logging, rate limits, monitoring, data contracts, and security review. This repo proves the shape and workflow, not a production deployment.

What would a safe pilot look like?

Start with read-only customer integration workflows: summary, tank detail, diagnostics, alerts, runout risk, monitor health, and webhook event definitions that can feed a customer dispatch or operations system. No operational writes at first. That proves customer value while keeping risk low.

What risks should matter most?

The main risks are data exposure, tenant isolation, unsafe write actions, auditability, and over-broad agent access. That is why the demo emphasizes read-only defaults, scopes, audit logs, and human approval for write actions.

Why build a working demo instead of sending a slide?

A working demo makes the idea concrete. It shows the field model, the command workflows, the API routes, the agent boundary, and the governance posture in inspectable code instead of abstract product language.

What is the ask?

The practical next step is a short product or technical conversation to determine whether a governed programmable layer around tank telemetry is relevant to roadmap, integrations, support workflows, or AI strategy.
